Verdict: request changes

Findings

Correctness — The core intent is sound: a remainingMinor of -23000 in the JSON output is confusing when the state already says "breached". The change (limit_minor - spent_minor).max(0) is trivially correct Rust. The state_for() function independently detects breaches, so the breach signal is not lost by clamping the remainder.

Test gaps (blocking) — Two existing tests break with this change and are not updated:

tests/budget.rs:36 — overspend_is_reported_rather_than_clamped asserts remaining_minor == -23_000; it gets 0. Needs to assert remaining_minor: 0 and verify state: Breached still holds.
tests/budget.rs:4 — spent_plus_remaining_always_equals_the_limit asserts spent + remaining == limit for all test cases including spent=73_000 against limit=50_000. With clamping at 0, spent(73,000) + remaining(0) ≠ limit(50,000). The test needs to either limit its data set to non-overspent cases or the invariant needs a new formulation.

Documentation (blocking) — Two doc comments directly contradict the new behavior and must be updated:

services/budget/src/lib.rs:98-99 — "Overspend is reported as a negative remainder rather than clamped to zero, because hiding it is how a breach goes unnoticed." With the state field independently tracking breaches via state_for(), this rationale is obsolete.
services/budget/src/lib.rs:5-6 — "spent + remaining == limit is an invariant the tests assert" — this invariant no longer holds for overspent budgets.

Scope — Focused single-line change. No scope issues.

Pattern-consistency — .max(0) is idiomatic Rust. No pattern concerns.
