Before any session

Follow the card, not the label

Note

The button that opens a session is not always called the same thing. A resting card offers Investigate, a card the factory is working offers Build, and Open session appears once a session exists and is idle. Whichever button is on the card is the one that opens what the run is doing. A guide that named a fixed button sent a presenter hunting for one that was not there.

Lightning lesson, sixty minutes

Design a Software Factory for Your Coding Agents

Architecture session. No live coding. The room leaves with a map they can hold against their own repository, and one named gap.

Ideas taught here: six layers, boundary, context, skills, execution, verification, delivery, the growing prompt.

Twenty minutes ahead, alone

Before anyone joins

Goal

The demo is warm and the console has data in it. Nothing here happens while people watch.

Say

Nothing. This segment is setup.

Run

$ make check
$ make score
$ make demo STEP=06

Check

  • The score prints and every phase is green.
  • The console is serving and lists finished runs with their timings.
  • Your editor is on a clean branch, because the harness will create worktrees and you want that visible.

Ask

Nobody. Confirm the room can read a terminal at the back before you start.

0:00 to 0:08

The afternoon that disappears

Goal

Everyone recognises the problem as theirs before any architecture appears.

Say

  • Open with the shape of the day, not the technology. The function took seconds. Then came re-explaining the codebase, checking what else moved, and tidying the pull request.
  • Name the wrong conclusion out loud: that the model needs to improve. Ask who has responded to a bad result by adding another paragraph to their instructions.
  • Land the reframe: the generator is not the missing piece. There is nowhere safe for it to run and no reliable way to brief it. Nothing checks its work before it reaches you.

Run

Nothing yet. Resist opening a terminal here.

Room sees

Slides or a whiteboard only. Faces, not a screen.

Ask

How long is your instructions file now, and when did you last read all of it?

0:08 to 0:28

The map

Goal

Attendees can name all six jobs and say which failure each one removes.

Say

  • Walk the six in order, giving each one a single sentence and a symptom. Do not define them abstractly; define them by what goes wrong when they are missing.
  • Spend the longest on the second and fifth, because those are where the room's pain actually is.
  • Say the sentence that reframes the hour. These fail separately, so the fix depends on which one is missing.

Run

Show the map in the workbook and scroll through it.

Room sees

  • The six-layer diagram, one heading at a time.
  • The symptom under each, said aloud rather than written on the slide.

Ask

Pick the symptom you had this week. Which job was missing?

0:28 to 0:40

Routing beats piling

Goal

The room understands why their instructions file stopped helping, and what replaces it.

Say

  • Describe the growth curve honestly. Each addition works, which is why it keeps happening, and accuracy still falls.
  • Explain the competition for attention. The sentence that matters is now one of forty, and thirty-nine do not apply to this task.
  • Show the alternative as a calculation rather than a philosophy. Files to be touched, owners of those files, rules for those owners, skills for that kind of work.

Run

$ make demo STEP=03

Room sees

  • Two tasks, side by side, receiving visibly different material.
  • The frontend task never being shown the money rules, and the reason why printed next to it.

Ask

What does a new engineer get told on day one that your agent is never told?

The same policy, read by a product

  • Name what is missing on purpose: nothing has run yet, so nothing on screen is a claim about quality.

The charter is not read by magic

Mastra Factory has no knowledge of a .factory directory. What it reads is AGENTS.md, and the only reason these rules bind anything is that the file points at them and repeats the protected list. Delete it and every limit here becomes a comment.

Both switches are off, deliberately

Arrival and action are separate. An issue landing on Intake is not a run starting, and the gap between those two is where a person decides whether this is work at all.

Six cards, one repository

Nothing on this board knows what the ledger is. It knows a repository was connected and that its issues arrive here.

  • Notices that Auto-start runs is off, so arrival and action are separate things.

Build Your First Software Factory Execution Harness

Ideas taught here: worktree per task, the branch as claim, limits, executor interface.

Thirty minutes ahead

Setup you do alone

Goal

0:00 to 0:08

The bug you handed to an agent

Goal

Everyone recognises an agent that edited a checkout they were working in, before any mechanism appears.

Say

  • Say what you are working on before how. The ledger is a screen that shows what each agent run cost, where its time went and how it ended. A page asks it for zero rows and gets an error, not an empty list. The terminal will name it as issue 2.
  • Put the comparison up. You hand it to an agent and carry on. By evening your files are half edited and your branch has moved.
  • Show the six layers with the execution layer lit. Boundary, context and skills come before it builds. Execution, verification and delivery come while it builds and after.
  • Say the session works alone and anyone can follow it. Then show the finished harness drawn whole.

Run

Slides only. Terminal open, nothing typed.

Room sees

  • The comparison between what you filed and what you found by evening.
  • One drawing of the six layers, with execution lit.
  • One drawing of the finished harness, before any part of it.

Ask

Who has lost work to a background run? What did it cost to recover?

0:08 to 0:21

A worktree for every task

Goal

Everyone has watched a task get its own worktree, a file written in it, and the main checkout stay clean.

Say

  • Collect the war stories first, then draw the shared checkout and the branch that moved. Each story is a missing place, not a misbehaving tool.
  • Run the demo for six minutes. Write a file in the new worktree, then show git status clean in the main checkout.
  • Open worktree.ts beside the terminal: the name comes from the item, so the same item always maps to the same branch.
  • Put the decision to the room: one shared checkout, or a worktree per task. Free and collides, against disk and an install and never.

Run

$ make demo STEP=02 create 2
$ git -C ../ledger worktree list
$ make demo STEP=02 remove 2

The implementation is steps/02-execution/worktree.ts. Ignore the make line that follows each run, it is make reading the argument as a target.

Room sees

  • Branch fq-2, a path under .worktrees, and the workspace count going from 0 to 1.
  • Two entries in the worktree list, then one again after the remove.

Ask

How many agent tasks would you run while you sleep, and where would each one install its dependencies?

0:21 to 0:34

Two runs, one item

Goal

They understand how ownership is settled without anything new to operate.

Say

  • Pose the collision before showing the answer: two scheduled runs wake up, both see issue 2, both want to push a fix.
  • Let someone propose a lock service, then price it: something to run, its uptime, and what happens when the holder dies.
  • Run the demo for six minutes. The remote is a throwaway bare repository, so the race is real.
  • Put the decision to the room: a lock service, or the branch you already have.

Run

$ make demo STEP=02 race 2

Read it in steps/02-execution/claim.ts: the push is never forced.

Room sees

  • Both runs computing fq-2, run 1 continuing, run 2 stopping with the remote's own rejected line.
  • A verdict saying exactly one run owns the work.

Ask

What else in your pipeline would be simpler if the coordination lived in a tool you already run?

0:34 to 0:47

What it can reach from in there

Goal

Attendees can state limits for one task in their own repository and know what happens when one is exceeded.

Say

  • Separate the two questions. A worktree answers where the work happens. Sandbox limits answer what it can touch once it is there.
  • Run the demo for six minutes. Read the profile table first, then the four refusals one at a time.
  • Insist on the ending: exceeding a limit stops the run, and a warning in a log is not a limit.
  • Put the decision to the room: limits the agent can edit, or limits it cannot.

Room sees

0:35 to 0:45

Somebody else's sandbox, same rule

Goal

They can say why an isolated checkout is a property of the harness rather than a courtesy.

Say

  • Two harnesses now: the one built in this lesson and the one inside the product.
  • Both give a run its own tree, for the same reason. In a shared tree you cannot tell two runs apart when one breaks.
  • Show where the checkout lives, and that deleting it costs nothing.

Run

$ ls ../mastra/.sandboxes || true

Show on the board

  • Work
  • to
  • a card in Building
  • to
  • its session
  • to
  • the file tree

A checkout of its own, every time

The session holds a clone under .sandboxes. Delete it while the run is going and the run dies; delete your own working tree and nothing happens, which is the whole point of the boundary.

The one that cost me an evening

A review once checked a pull request out in the Factory server's own directory rather than a sandbox. The files docker-compose.yml and package.json vanished, and the only symptom was "compose file is invalid". Ask the room where they would have looked first.

Sandboxes are cattle

They are named by run, not by branch, and nothing in them is worth keeping once the pull request exists.

Room does

  • Opens the sandbox directory and confirms it is a real clone.
  • Confirms their own working tree has no new branch.

Ask

What breaks first if two runs share one checkout: the build, the test, or the diff?

0:35 to 0:45

A reviewer that can say no

Goal

They accept that a reviewer which never rejects anything has not been tested.

Say

  • The interesting artefact is the refusal, not the approval.
  • Read the two findings aloud and note that one of them is a weakened assertion, which no path rule could have caught.
  • This is why the charter forbids editing a test to turn a suite green. It is a property of the change, not of a filename.

Run

$ make lab-reset

Show on the board

  • Review
  • to
  • the pull request
  • to
  • Conversation
  • to
  • the verdict line

The verdict is the first line, on purpose

A reviewer that buries its conclusion in prose cannot be checked by anything. One line, one of two values, and everything after it is the argument for it.

A weakened assertion is not a path rule

Changing toBeCloseTo(1, 10) to toBeGreaterThanOrEqual(0) touches no protected file. No glob catches it, which is why the charter forbids it in words and the reviewer has to be the thing that notices.

A picture is the one artefact a test cannot read

Four screenshots in this repository were a loading spinner, and every assertion around them passed. Show the room the guard that refuses to photograph a page still saying it is loading.

  • Identifies which finding a glob could have prevented and which it could not.

The evidence travels with the change

The plan the run wrote is committed beside the diff, so a reviewer who watched none of it can see what was intended before reading what was done.

Nothing merges itself, on any tier

Every route in this material ends at an open pull request. The charter says so and the four shapes do not argue about it.

A decision is not the work

Cohort module one, two hours

Design Your Software Factory Architecture

Everyone arrives with a repository they are allowed to change. They leave with a written policy for it that a run can read, and that they could defend in a design review.

Ideas taught here: the charter, autonomy by consequence, protected paths, back-pressure, the ownership graph.

0:00 to 0:20

Their repository, not mine

Goal

Each person has named the area of their codebase where an error would be most expensive.

Say

  • Set the rule in the first minute. Every exercise happens on their code. The lab only shows a worked example.
  • Ask them to write down the single directory they would least like a machine to edit, and why it earns that.
  • Collect three answers aloud. The reasons differ, and hearing that is what stops the policy becoming a template they copy.

Run

$ git clone <their repository> && cd <repository>
