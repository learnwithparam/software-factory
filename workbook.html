Overview

Why is a better prompt not enough?

The agent writes good code. Why does it still go wrong?

Most days the code looks fine. Then one day it edits the wrong file, or ships something nobody checked.

So we stop tuning the agent and build jobs around it. There are six. Each answers one question.

Most teams already own two or three of them by accident. The work is finding the one that is missing.

Six jobs sounds like work. Surely one more line in the prompt is cheaper?

Why not fix each mistake with one more line in the prompt?

It works, so you do it again. A year later the prompt is a small book.

Every task pays to read that book, and most need one page of it. The line that matters now competes with forty that do not.

So we route instead of piling. A task is given what governs the files it will touch, and nothing more.

The price is a router to maintain. We build it in the context chapter.

Routing needs an agent to run the work. Which agent should we build all this around?

Which agent should we build all this around?

Models change every few months. A system bolted to one of them dies with it.

So the factory never learns which model runs. It only needs something it can start and wait for.

export interface Executor {
	readonly name: string
	run(request: Request): Promise<Response>
}

Swap the model and nothing above it changes. A replay stand-in makes the whole test suite cost nothing, with no network.

The agent is chosen. Next: what may it try without asking?

Layer one

What may the agent try without asking?

What may the agent do while nobody watches?

Someone decides this every time an agent starts. Usually nobody says it aloud.

So we write it down, and make it a question the code can ask. The answer is either yes, with limits, or no, with a reason.

export type Decision =
	| { allowed: true; autonomy: Autonomy; targets: string[]; affected: string[] }
	| { allowed: false; reason: string; rule: string }

Writing it costs one page. The first surprise without it costs far more.

A written rule needs a home. Where do the rules live, and who may edit them?

Where do the rules live, and who may edit them?

Rules scattered across prompts and wikis get out of date. Then nobody knows which one the agent read.

So one file holds the rules, and the factory reads it before every run. It stays brief, because nobody rereads a long policy.

Only people edit it. A rule the agent can rewrite is not a rule.

One tier for the whole repo is too blunt. What should freedom follow?

What should the agent's freedom follow?

The instinct is small changes unattended and big ones reviewed. That is the wrong axis.

So freedom follows the worst outcome, not the size. How bad is it if this is wrong, and how easily is it undone? Grade that by area, not by repository.

const strictest = written.reduce((worst, target) =>
	STRICTNESS[target.autonomy] > STRICTNESS[worst.autonomy] ? target : worst,
)

A task that spans two areas gets the stricter answer. Somebody has to write the grades down, area by area.

Some areas deserve more than a grade. Which paths must never be touched?

Which paths must never be touched?

The place where a mistake costs most is the place an agent will eventually reach.

So the charter lists them, each with a reason. Credentials, the money path, the graph itself, the checks. A task that needs one is not lost. It goes to a person.

target/services/budget/**      # the money path, and a wrong answer here is expensive and slow to notice
target/project-graph.json      # editing the graph would widen every other rule in this file
steps/01-boundary/CHARTER.md   # limits an agent can edit are not limits
.github/**                     # a workflow change can switch off the checks everything else rests on

	for (const entry of repo.charter.protectedPaths) {
		if (matcher(entry.glob)(path)) {
			return { allowed: false, reason: entry.reason, rule: `protected: ${entry.glob}` }
		}
	}
}

A protected path nobody has watched refuse a task is a comment. The lab keeps one task that must be refused.

Refusing costs nothing. Approving costs attention. How many items may wait on a person?

How many items may wait on a person?

Your first productive afternoon ends with more pull requests than anyone will read. That looks the same as building nothing.

So the limit is not how many agents can run. It is how many decisions wait on a person. The charter sets a cap, and a run refuses to start when the queue is full.

const cap = repo.charter.reviewQueueCap
if (awaitingReview >= cap) {
	return {
		allowed: false,
		reason: `${awaitingReview} items already wait on a person, and the cap is ${cap}. The limit is review attention, not generation.`,
		rule: `STOP_IF: awaiting_review >= ${cap}`,
	}
}

The cost is idle capacity. That is the right thing to have.

A cap needs owners to route to. Who owns each path?

Who owns each path?

A rule written over path patterns goes vague as a repo grows. Nobody can say which rule covers the new folder.

So we keep a graph. Each target owns some paths, has an autonomy level, and lists the commands that check it. The rule becomes: this area, this owner, these checks.

It also makes a gap loud. Nobody chooses a default for a folder no one owns.

Paths have owners. Next: what does the agent need to be told?

Layers two and three

What does the agent need to be told?

Why does the agent get familiar code wrong?

It is clever enough. But nobody told it the things everyone on your team already knows.

So we hand it the missing facts along with the task. Agents rarely fail for want of brains on a familiar codebase. They fail for want of these facts.

Facts describe one repository. Next: how do we teach a way of working once?

How do we teach a way of working once?

A good review checks the same six things every time. Somebody retypes them into every prompt.

So we keep a skill: a procedure worth reusing, saved apart from any one prompt. How to add a migration. What a review looks for. What proof ends the job.

A skill helps only if it arrives. Next: who decides what each task sees?

Who decides what each task sees?

Someone must pick what each task reads. A person doing it by hand gets it wrong on a Friday.

So a small piece of code does it. It reads which files the task will touch, asks the graph who owns them, and builds the package. It also writes down what it left out.

export interface Context {
	readonly issue: Issue
	readonly rules: Rule[]
	readonly skills: Skill[]
	readonly commands: Command[]
	/** What the router deliberately left out, and why. */
	readonly withheld: Array<{ what: string; because: string }>

Because it is code, you can test it. Give it a task and check what it routed. That is knowing, not believing.

The router picks skills. Next: why do step-by-step skills break?

Why do step-by-step skills break?

So you script every move. The result is long, brittle, and worse than the agent's own judgement.

So a good skill names three things and stops. The result you want. The constraints nobody could guess. The proof required at the end.

Skills tell the agent how to work. Next: do we run every check on every change?

Do we run every check on every change?

Running everything is so slow that people stop. Running one suite passes while a shared contract quietly breaks.

So we work out the affected set from the diff and the dependency edges. It is the same graph the router used. The edge to watch is the shared one.

The checks are chosen. Next: where does the work happen?

Layer four

Where does the work happen?

Where should the agent actually work?

The easy answer is your own checkout. It is also why people stop trusting background work.

None of that is the agent behaving badly. It just has nowhere of its own to work. So we give it a place.

The agent needs a place of its own. How do we give every task one?

How do we give every task its own place?

Copying the whole repo per task is slow. Sharing one checkout is how tasks collide.

So we use git's own answer. Two tasks cannot interfere. A failed run leaves a worktree you can inspect, not a mess in your working copy.

const existing = git(['branch', '--list', workspace.branch], repo)
if (existing.trim() === '') {
	git(['worktree', 'add', '-b', workspace.branch, workspace.path, from], repo)
} else {
	git(['worktree', 'add', workspace.path, workspace.branch], repo)
}
return workspace

Cleanup is one command, not a careful sequence.

Two runs may wake up for the same item. Who owns it?

Who owns an item when two runs wake up?

Both start on the same issue. Now you have two half-finished answers and a merge to untangle.

A lock table is one more service to run. So we use a name instead. Both runs work out the same branch name from the item. The first push wins, and the loser stops.

export function branchFor(item: string | number): string {
	const slug = String(item)
		.toLowerCase()
		.replaceAll(/[^a-z0-9]+/g, '-')
		.replaceAll(/^-|-$/g, '')
	if (slug === '') throw new Error('an item needs a name a branch can be derived from')
	return `fq-${slug}`
}

There is no force flag to pass, on purpose. This is where a script turns into a system.

The claim is settled. Next: what can the agent reach from its own place?

What can the agent reach from its own place?

A worktree does not stop it deleting your home directory, or calling out to the internet.

So we state limits per task. Which paths it may write, which commands it may run, and whether anything may leave the machine. Component work gets no network. The task that regenerates a lockfile does.

display: {
	write: ['apps/console/**'],
	commands: ['bun', 'git', 'node'],
	network: false,
	why: 'Display work reads the ledger and renders it. It needs no network and no other service.',
},

Two rules keep this honest. The limits sit where a person can read them. And breaking one ends the run.

The agent is fenced in. Next: what must be proven before a person looks?

Layer five

What must be proven before a person looks?

How do we keep plausible wrong code from review?

Agents write code that reads correctly. Plausible wrong code costs a reviewer more attention than code that is plainly wrong.

So a person looks last. Every check a machine can run happens before any human attention is spent.

Verification is a stack of checks. Next: who says the checks passed?

Who says the checks passed?

The agent says everything passed. That is a claim, and nobody checked it.

So one script runs the checks and ends with one exact line. The line is evidence. The agent's summary is only a claim.

function result(state: State, detail: string, runs: CheckRun[]): GateResult {
	return {
		state,
		line: `VERDICT: ${state} ${detail}`,
		runs,
		exitCode: state === 'PASS' ? 0 : state === 'FAIL' ? 1 : 2,
	}
}

The case that earns its keep is a missing check. A repo with no test command must not turn green.

if (!ranATest) {
	return result('MISCONFIGURED', 'no test command ran, so this run proves nothing about behaviour', runs)
}

It says misconfigured and stops. A repo that is not wired up cannot ship yet. That is the point.

Green shows the script ran. Next: who tests the tests the agent wrote?

Who tests the tests the agent wrote?

The agent writes the tests, then makes them pass. A green suite proves the code agrees with itself.

So we keep a few behaviour checks out of its reach and run them afterwards. They do not replace the tests written with the change. They are the independent sample.

name: 'a run list is bounded even when nobody asks for a limit',
run: async (base) => {
	const runs = (await json(`${base}/runs`)) as unknown[]
	if (!Array.isArray(runs)) return 'the list is not an array'
	if (runs.length > 200) return `returned ${runs.length} rows with no limit applied`
	return undefined
},

Keep them few, or they turn into a second suite.

Holdouts test behaviour. Next: who reviews the change without hearing the story?

Who reviews the change without hearing the story?

A reviewer told what was attempted starts confirming it. It stops checking.

So the reviewer starts fresh, holding only the code that changed and the request. It cannot lean on what the writer meant.

The reviewer reads the diff. Next: how do we know a new test can fail?

How do we know a new test can fail?

A test that has never been red is not known to test anything.

So we do the one check no gate can do. Undo the change the test was written for. Watch the test go red. If it stays green, it was never connected to the behaviour, and the run says so.

// The evidence rule. A pass with no reverted proof is not a pass.
if (evidence.negativeProof === undefined) {
	downgrade('needs-review', 'no test was shown to fail without the change')
} else if (!evidence.negativeProof.redWithoutChange) {
	downgrade('fail', `${evidence.negativeProof.testName} stayed green while its subject was broken`)
}

It costs one extra run of one test. It also needs no agents at all, so it is the most portable idea in this book.

The proof sits on disk. Next: who decides what the verdict may claim?

Who decides what the verdict may claim?

The agent finishes talking. What it said becomes the verdict a person acts on.

So ordinary code decides, after the agent stops. It reads what the run left on disk. What the agent said about the run is never consulted.

// The quotation rule. The reviewer must reproduce the gate's line exactly.
if (claimed.gateLine.trim() !== evidence.gateLine.trim()) {
	downgrade('needs-review', 'the quoted gate line does not match the one the gate wrote')
}

The rules read the run. Next: what if one definition lives in three languages?

What if one definition lives in three languages?

A type is copied into Go, Rust and TypeScript. The copies drift, and production finds out.

So we keep one definition and assert every implementation against it. That gives the cross-stack task a real shape.

A failed check comes back as a bare rejection. So the next attempt repeats the mistake.

So one agent writes and another judges. When the judge says no, it also says what broke and in which file, so a retry begins with a clue. That is what makes it cheap.

What stops a loop that cannot succeed?

A task that cannot be done keeps burning attempts. Somebody notices, and the first thing they see is the bill.

So every loop declares its endings up front. The result always names which one happened.

The loop now ends. Next: where does the time actually go?

Where does the time actually go?

The factory feels slow. The only lever anyone reaches for is a faster model, which is the one thing you do not control.

So we time every stage on its own. The surprise on a first real run is that writing code is rarely the slow step. Time hides in setup, in repeated checks, and in waiting on a person.

Each stage also has a limit. Going over it ends the run.

Now we know the time. Next: how does finished work reach a person?

Layer six

How does finished work reach a person?

Where does work go when the code is written?

Most demos stop when the code is written. That is exactly where trust is built or lost.

So we design the last mile on purpose. Work must arrive where a person already looks, with enough proof to judge it.

Both ways back and the way out are outcomes we plan for, not surprises.

The path is set. Next: where does the queue live when a session dies?

Where does the queue live when a session dies?

A run dies halfway. Whatever it knew died with it.

So the state lives in the issue tracker, where people already look. The next run and a curious human can both read it. Neither needs the conversation that made it.

The state is durable. Next: what does the reviewer see first?

What does the reviewer see first?

A bare diff asks the reviewer to trust the work. Checking it becomes the reviewer's whole job.

So the unit of delivery is a draft pull request that carries its own proof. Draft is deliberate. It says a machine made this and no person has stood behind it yet, which is true.

The proof is attached. Next: can anything merge without a person?

Can anything merge without a person?

Ten green runs in a row is not permission. Neither is a high confidence score.

So no tier, no score and no winning streak changes this. Hooks catch the obvious routes. The rule that counts is branch protection, because a guardrail an agent can edit is not a boundary.

The factory does not remove the reviewer. It makes sure the machine did all it could before the reviewer arrives.

A person decides every merge. Next: how do we know the factory is working?

How do we know the factory is working?

Someone asks whether the factory is helping. Nobody has a number.

So every run writes one file, and nothing rewrites it. Compare the tenth run with the first and opinion becomes measurement. The console in this repo reads these files.

That is one factory. Next: who does what in a team like yours?

Four company shapes

Who does what in a team like yours?

Who makes which decision?

The four profiles look like a table of permissions. They are really four ways to share the same jobs between people.

No shape is more advanced than the others. Each moves the same decisions to different people, and each pays for it somewhere. A team that cannot say which shape it is will get whichever one the tool shipped with.

Solo

One person files, decides, reads and merges. So the factory starts its own runs and approves its own plans. A gate between a person and themselves is ceremony.

The queue cap is one. Three things waiting is not three times the output. It is a bottleneck with a backlog. The money path is build, because the gate has moved to the merge, where this person reads every line anyway.

Startup

A few people file and one accepts. Runs still start on arrival, but plans no longer approve themselves. A small team shares the cost of a mistake without sharing the context that prevents it, so somebody reads the approach before code exists.

The queue cap is three, and the money path is propose. Past three, the person accepting plans is the limit.

Scaleup

Teams own areas. A person on the owning team starts each run on purpose. The money path is refuse, because an item that reaches it belongs in that team's queue, not in a plan from whoever filed it.

The person who decides is now not the person who noticed. The ownership graph writes that down, so nobody argues it on the day. The queue cap is five.

Enterprise

Nothing is planned until a person accepts the item. The tier is controlled, not supervised, so work does not begin on arrival. The money path is refused and protected. The agent may investigate and propose.

The queue cap falls to two. The limit is no longer how many plans a team can read. It is how many changes a change process can carry.

Measured, not asserted

Does the agent obey a rule written in a prompt?

Everything above says how the factory should behave. This chapter shows how one behaved on the runs behind this material.

What happens to the same change in two systems?

The hand-built pipeline calls decide() before anything runs. Mastra Factory tells the agent about the same graph in AGENTS.md, then dispatches.

The cleanest evidence is the boring route: an issue asks for a Contributing section in the README. The agent planned it, built it, and opened a pull request, and the screenshots show it approved. Then 01-clean-path.spec.ts gives the same changed files to decide() and gets REFUSE. README.md has no owner, so it falls to the repo target, which refuses.

Run the same route again and the agent does not always choose the same. It advanced its own plan on one run and waited on the next. That is the dangerous part. Your demonstration passes, your pilot passes, and the run that matters is the one nobody watched.

A limit that depends on the agent choosing to obey it is a limit you have already lost.

What did the runs not honour?

Each row was recorded by the suite and written to evidence/prompt-vs-gate.json. tests/findings.test.ts fails if this page cites a finding no run produced. It also fails if a run recorded an ignored instruction and this page leaves it out.

The last column says how well each row is evidenced. The record means the counter watched it fail on a counted run. PR 544 and PR 547 are open pull requests you can go and read.

Seen while building happened once and left nothing behind. Treat those as a warning about what the system permits, not a rate.

What does each miss cost, and what do we do instead?

An advisory level. If propose cannot hold work at the boundary, the graph is only documentation. Do not write a firmer sentence in AGENTS.md. Run a check on the diff before merge, reading the same graph, and it works whatever agent you buy.

A silent refusal. A stalled issue looks the same as a declined one. Anything that stops should say so where a person already looks.

A model that guesses. "Ask when unsure" needs the agent to notice it is unsure. Use a rule that needs no noticing: an issue that names no owning service never reaches build.

Two forms of one verdict. A comment and a label will disagree. Pick one as the record and derive the other.

Grounding

What has the field measured?

The claim in this workbook is that the generator is not the missing piece. That is a claim about the world, so we hold it against measurements, not against how a good demo feels.

Does using AI make delivery better?

Adoption is nearly universal. Whether it helps is the part to check.

DORA's 2025 research reports that nine in ten technology professionals use AI at work. About a third say they trust the code little or not at all. Higher adoption goes with more throughput and more instability, together.

So AI is an amplifier. It magnifies a strong platform and a weak one. Generation got cheap while verification and delivery did not change, and those two layers decide whether faster work also arrives working.

Faster work is not always better work. Next: does feeling faster mean being faster?

Does feeling faster mean being faster?

Developers using AI said they felt faster. A stopwatch said otherwise.

METR ran a randomised trial. Sixteen experienced open-source developers worked 246 real tasks in code they knew. They took 19 percent longer with AI, and guessed afterwards they had been about 20 percent faster.

Two caveats apply. These were experienced maintainers on familiar code, the case least likely to gain, and the tools were from early 2025. What survives is the gap between felt and measured, about forty points. A team judging by how the last demo felt is using that instrument.

Feelings are a poor instrument. Next: which risk does each layer remove?

Which risk does each layer remove?

A security reviewer asks what each layer protects against. Trust us is not an answer.

So we map the layers onto a list the reviewer already holds. OWASP published its Top 10 for Agentic Applications in December 2025. It covers threats that belong to agents, not to models.

In every row the thing doing the removing is code. A function refuses, a worktree contains, a gate blocks, and a person merges.

Each layer answers a named risk. Next: who else routes context instead of piling it up?

Who else routes context instead of piling it up?

The context router can look like our own invention. It is published practice.

Anthropic's guidance on effective context engineering names three techniques for work that outgrows a context window. They are compaction, structured notes, and sub-agents that return a summary.

All three make the same move as the router here. Decide what this task needs, give it that, and keep the rest out, instead of adding a paragraph every task pays for.

Three techniques, one move. Next: which patterns outlast the products?

What survives the products

Which patterns outlast the products?

Both systems in this repository will be replaced. These will not. Each pattern says the problem, why it is hard, the fix, what the fix costs, and where it lives in the built and bought versions.

A prompt is not a gate

Problem
The rules an agent must follow have to be written down somewhere, and the obvious place is the prompt the agent reads.
Why it is hard
A prompt is the cheapest place to put a rule, it needs no code, and it reads convincingly to whoever wrote it. A gate costs work and has to be maintained. Meanwhile the agent complies often enough that the difference stays invisible until the run that matters.
The fix
Write every rule twice. Once in the prompt, so the agent knows what is wanted, and once as code that runs before or after the work and can refuse it. If the second copy does not exist, say out loud that the rule is advice.
It costs
Two places to change when a rule changes, and a test that holds them together.
In this repo
steps/01-boundary/policy.ts reads the ownership graph and refuses before any agent starts, which is why make prove can break it on purpose and watch it fail.
On a platform
The same graph is described to the agent in AGENTS.md and consulted by nothing. The run recorded in the findings built a refused path and skipped an acceptance step, both while being told not to.

The executor is an interface

Problem
Every part of the system needs an agent to do work, and binding to one makes the whole thing a wrapper around a product that will change.
Why it is hard
Testing wants determinism and no spend. Teaching wants a real agent. Buying wants the freedom to change the agent later. All three pull against hard-coding one.
The fix
Define an executor as any command that takes a prompt on standard input and exits. Everything above it depends on the interface, never on the product.
It costs
One indirection, and usage figures an agent reports rather than ones you measured.
In this repo
steps/lib/executor.ts, with a replay executor that makes make check free and offline.
On a platform
The agent role on a working phase. Swapping the model is a settings change rather than a code change.

The name is the claim

Problem
Two scheduled runs wake up for the same item and both start work on it.
Why it is hard
A lock table is correct and is a service to operate, with an availability story and a question about what happens when a holder dies.
The fix
Derive the branch name from the item so both runs compute the same one, and push without force. The first push creates the ref and the second is rejected.
It costs
Nothing, unless somebody adds a force flag, which is why there is no flag to pass.
In this repo
branchFor() in steps/02-execution/worktree.ts, proven by a real push race in the tests.
On a platform
The server owns session identity, so the race does not arise. The idea still applies to anything you schedule yourself.

A missing check is louder than a failing one

Problem
A repository with no test command produces a run that looks exactly like a passing one.
Why it is hard
Absence and success are indistinguishable from outside. Treating absence as success is the default in almost every pipeline, because it takes no code.
The fix
Make the gate report three states rather than two. Missing is neither a pass nor a failure, and it stops the run.
It costs
A repository that has not finished wiring its checks cannot ship through the factory yet, which is the point.
In this repo
steps/04-verification/gate.ts returns MISCONFIGURED with exit 2.
On a platform
A tool result rule reading the verdict, which refuses to read a missing check as either outcome.

One line nothing may restate

Problem
An agent reports that the checks passed, and that report is the only thing anyone reads.
Why it is hard
An agent summarising is useful everywhere except in the sentence somebody will act on.
The fix
End the gate with one exact line. Downstream may quote it and may not paraphrase it, and a quotation that does not match the original is a downgrade.
It costs
Slightly stilted output, and a rule people have to be told once.
In this repo
VERDICT: PASS every selected check passed, compared exactly in judge().
On a platform
The same line, carried in the tool result the rule reads.

Tests the writer never saw

Problem
The same run writes the code and the tests, so a green suite means the code agrees with itself.
Why it is hard
Tests written with the change are the most useful ones to have. They are also the least independent.
The fix
Keep a small set of behavioural checks out of reach of the implementing agent and run them afterwards.
It costs
A second place to maintain, and it must stay small or it becomes a second suite.
In this repo
steps/04-verification/holdout/, outside the target and never routed.
On a platform
A checking phase whose role has different tools from the building one.

The writer never grades the work

Problem
The thing that produced a change is the worst judge of whether it is right.
Why it is hard
The account of how work went is genuinely useful context, and it is also what makes a reviewer confirm rather than check.
The fix
Give a second agent the task and the diff, and deliberately not the story of the attempt.
It costs
Minutes per change, and occasional rejections of work that was fine.
In this repo
judge() in steps/04-verification/verifier.ts, with recorded reviews.
On a platform
The Review board, which gives a pull request its own session rather than continuing the authoring one.

Undo the change and watch the test fail

Problem
A test that has never been red is not known to test anything.
Why it is hard
Nobody wants to break working code to check a test. It is also the only check that proves the test is connected to the behaviour.
The fix
Revert the change, run the new test, require red, restore. Do it every time rather than when somebody remembers.
It costs
One extra run of one test.
In this repo
make demo STEP=04 -- negative-proof, which does it for real on a scratch module.
On a platform
Not built in. It is a step you add to the checking role, and the most portable idea here.

Code decides what a verdict may claim

Problem
The result a person reads is whatever the agent decided to say.
Why it is hard
Investigation needs freedom. The sentence somebody acts on needs none at all.
The fix
After the agent stops talking, ordinary code reads the artifacts the run left and downgrades any claim whose proof is missing.
It costs
The rules have to be written, and each one needs a reason.
In this repo
judge(): no reverted proof, no holdout, or a misquoted gate line all downgrade.
On a platform
A tool result handler, which sees what a tool returned rather than what was said about it.

The limit is review attention

Problem
Generation is cheap, so the queue of things waiting for a person grows without bound.
Why it is hard
More agents feels like more throughput. The binding constraint is one person understanding a change well enough to stand behind it.
The fix
Cap how many items may wait on a person, and refuse to start work when the cap is reached.
It costs
Idle capacity, which is the correct thing to have.
In this repo
STOP_IF: awaiting_review >= n in the charter, checked before anything else runs.
On a platform
Not built in. It is yours to add, and it is the first thing people delete.

Freedom follows blast radius, not size

Problem
Deciding what an agent may do unattended by how big the change is.
Why it is hard
Size is easy to measure and is the wrong axis. A ten thousand line migration on an unlaunched project is safer than fifty lines in a payment path.
The fix
Grade autonomy by how bad the worst outcome is and how easily it is undone, per area rather than per repository.
It costs
Somebody has to decide, area by area, and write it down.
In this repo
The autonomy column in .factory/targets.json, with a reason beside each.
On a platform
A transition policy, which can also demand recorded acceptance before code exists.

Some paths are never touched

Problem
The area where a mistake is most expensive is the area an agent will eventually touch.
Why it is hard
A blanket refusal stops the factory being useful. No refusal at all means the first surprise is the expensive one.
The fix
List the paths that are never modified unattended, each with the reason, and have the list protect itself.
It costs
A route for work that legitimately needs those paths, which is a person.
In this repo
The protected block in the charter, which protects the charter and the graph beside it.
On a platform
The same list, expressed in the policy that allows or rejects a move.

Route, do not pile

Problem
The instructions file grows every time something goes wrong, and accuracy falls as it grows.
Why it is hard
Each addition works, which is why it keeps happening. The sentence that matters is now competing with forty that do not apply.
The fix
Compute what a task receives from what it will touch: the rules for those areas, the skills for that kind of work, and nothing else.
It costs
A router to maintain, and the discipline to keep it small enough not to need a diagram.
In this repo
steps/03-context/router.ts, which records what it withheld beside what it included.
On a platform
The prompt a skill invocation builds, plus the repository the sandbox checks out.

Hand back the reason, not the rejection

Problem
A failed check comes back as a status, so the next attempt repeats the mistake.
Why it is hard
One agent grading its own output has already spent its reasoning defending it.
The fix
Split the roles. The tester returns what failed, where, and what should have been true, and the next attempt starts from that.
It costs
Two roles to run, and a loop that needs declared endings or it will not have one.
In this repo
handback() in steps/05-loop/loop.ts, with attempt and time budgets.
On a platform
A retry outcome on the checking phase, routing back to building.

Separate where work is from who decides

Problem
Process and permission get tangled, so changing one changes the other by accident.
Why it is hard
A board is about where work is. A policy is about who may move it. Mixing them makes every rule a layout change.
The fix
Declare phases and the moves between them, then declare separately which moves a person must make.
It costs
Two things to read instead of one, and worth it the first time the process changes.
In this repo
The graph declares areas and the charter declares who decides, and neither restates the other.
On a platform
defineBoard() for phases, transitionPolicy for who may move a card.

Bought instead of built

What changes when you buy it?

Do the platform's phases match the layers?

A hosted factory shows a board of stages. It looks like a different system.

So we lay one over the other. Entering a stage starts an agent in a declared role, and leaving it runs an action. The match to what this repository builds by hand is close to one to one. That is why we built it by hand first.

Now the buy is an engineering decision. You are not choosing between a product and nothing. You are choosing who maintains the parts you understand.

Who still owns the policy on a platform?

The platform brings a board, sandboxes and sessions. It cannot know what your team may merge unattended.

So the last step is not a migration. It is the same charter written against a different substrate. On a platform it becomes a function that allows or rejects a move. That is the honest test of whether the architecture was real.
