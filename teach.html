Overview

What a factory is, and why a better prompt is not one

The six layerssix-layers

A coding agent on its own is a generator. Around it sit six jobs that decide whether its output is worth your attention. Boundary says what may be attempted. Context says what the task gets to know. Skills hold the know-how that is reused rather than retyped. Execution says where the work happens and what it can reach. Verification says what proof must exist. Delivery says how finished work reaches a person and who decides it ships.

Naming them separately matters because they fail separately. Work that keeps arriving wrong is usually a context problem. Work that arrives plausible but broken is a verification problem. Work that damages something is a boundary problem. One word for all three leaves you tuning a prompt when the missing piece is a gate.

The layers are not a maturity model. Most teams already have two or three by accident, written down nowhere. The exercise is finding which one is absent.

Why the prompt keeps growingmega-prompt

The usual response to an agent getting something wrong is to add a sentence to the instructions. It works, so it happens again, and the instructions become a document that every task pays for and no task needs in full. Accuracy falls as the pile grows, because the sentence that matters for this task is now competing with forty that do not apply to it.

Routing replaces piling. Each task receives the repository rules that govern the files it will touch, the skills its kind of work needs, and the task itself. What a task does not need, it never sees.

The executor is an interfaceexecutor-interface

Nothing in the factory knows which agent runs the work. An executor is any command that accepts a prompt on standard input, does something to a working directory, and exits. That indirection buys three things: the loop can be tested against a recorded transcript with no model and no network, a different agent can be swapped in without touching policy, and the same task can be replayed to compare two agents on identical input.

It is also the honest boundary of the claim. The factory is not a model. It is the system that decides what a model is allowed to attempt and what happens to the result.

Run make check and no model is called. The same loop, the same policy, the same gates, a recorded agent.

Layer one

Boundary: what may be attempted without asking

Boundaryboundary

Boundary is the answer to a question every team answers informally and inconsistently: which work can an agent finish while nobody is watching. Left implicit, the answer drifts by person and by day, and the first surprise is expensive. Written down, it becomes something a run can read before it starts, and something a reviewer can point at afterwards.

The chartercharter

One file, owned by a person, that the factory reads before every run. It states the tier, the paths that are load-bearing, the kinds of task that may proceed unattended, what counts as finished, and the conditions under which the factory stops producing. It is short on purpose. A policy nobody rereads is a policy that stops describing the team.

The agent may not edit it. A proposed change to the charter is a pull request a human reads like any other, which is the only way the limits stay meaningful.

Autonomy tracks consequenceautonomy-tier

The instinct is to grant freedom by difficulty: small changes unattended, large ones reviewed. That is the wrong axis. A large migration on a project with no users is recoverable. A small edit to the code that decides what a customer is charged is not. Freedom should follow how bad the worst outcome is and how easily it is undone.

So the tier is a property of the repository, and it is refined per area. In this lab the budget engine is always human-approved whatever the size of the change, and the console can be changed unattended even when the change is large.

Protected pathsprotected-path

A list of globs the factory will not modify on its own. Credentials and configuration, the money path, anything that governs the factory itself, and the tests that define existing behaviour. A task that needs one of them is not refused forever; it is routed to a person who decides.

The useful property is that a refusal is visible. A run that stops with a reason is information. A run that quietly rewrites an assertion so its own work passes is the failure this list exists to prevent.

A protected path nobody has watched refuse a task is a comment. The lab keeps a task that must be refused, and scores the refusal.

Back-pressure is a numberqueue-cap

The constraint on a factory is not how many agents can run. It is how many decisions are waiting on a person. Generation is cheap and getting cheaper; the attention needed to understand a change, integrate it, and take responsibility for it is fixed.

So the charter carries a cap on how many items may sit awaiting review, and a run refuses to start work when the queue is full. Without it the first productive afternoon ends with more pull requests than anyone will read, which is indistinguishable from having built nothing.

Every path has one ownerownership-graph

Policy stated over globs alone gets vague as a repository grows. A graph of targets, each owning a set of paths and naming the commands that check it, makes the policy specific: this area belongs to this target, the target has this autonomy, and these are the checks that must pass for it.

It also makes a gap loud. A directory that no target claims is a directory with no owner, no checks and no autonomy rule, and the build fails rather than guessing.

Layers two and three

Context and skills: what the task is told

Contextcontext

Context is everything the task needs to know that is not the task. Where the code lives, how this repository does things, which invariants are not negotiable, what the surrounding code already looks like. Agents rarely fail for want of intelligence on a familiar codebase; they fail because nobody told them the thing everyone on the team already knows.

Skillsskills

A skill is a procedure worth reusing: how to add a migration here, how to write a test that will still make sense in a year, what a review looks for. It says what good work is and what evidence proves it, and leaves the mechanics to the agent. Kept separately from any one prompt, it improves once and every task gets the improvement.

The distinction from context is worth holding. Context describes this repository. A skill describes a way of working, and often survives being copied to a different repository unchanged.

The context routercontext-router

A small piece of code that turns a task into the exact material that task should receive. It reads which files the work is expected to touch, asks the ownership graph which targets those belong to, and assembles the rules, the skills and the task description for that combination.

Being code rather than prose, it can be tested. Give it a task and assert what it routed. That is the difference between believing the right context arrived and knowing it did.

A skill states the outcome, not the keystrokesreusable-skill

The failure mode when writing one is to script every move, which produces something long, brittle, and worse than the agent's own judgement. The version that holds up names the outcome, the constraints that are not obvious, and the evidence required at the end.

Only what the change touchesaffected-targets

Running every check in a repository of any size is slow enough that people stop doing it. Deriving the affected set from the diff and the dependency edges keeps the loop fast, and it is the same calculation that tells the router which rules a task needs. One graph, two uses.

The edge that catches people is the shared one. A change to a contract that three services are built against affects all three, and a naive file-to-target mapping will run one suite, pass, and ship a break.

Layer four

Execution: where the work happens

Executionexecution

Giving an agent your checkout is the default because it is the path of least setup, and it is the reason most people stop trusting background work. Two tasks collide. A half-finished experiment gets committed. You switch branches under a run and it writes into the wrong one. None of that is the agent behaving badly; it is the absence of a place for it to work.

A worktree per taskworktree

Git already solves this. A worktree is a second checkout of the same repository at a different commit, sharing one object store, created in about a second and removed as easily. Each task gets one, does its work there, and it is thrown away when the task ends.

The properties that matter: your own branch is never touched, two tasks cannot interfere, a failed run leaves an inspectable directory rather than a mess in your working copy, and cleanup is a single command rather than a careful sequence.

The branch is the claimbranch-claim

When more than one run can start for the same item, something has to decide which one owns it. A lock table is a service to operate. A deterministic branch name pushed to the shared remote is not: the first push wins because the remote rejects the second, and the loser stops.

This is worth dwelling on when teaching, because it is the moment the design stops being a script and starts being a system. Coordination came from a tool everyone already runs, and there is nothing extra to keep alive.

Limits on files, commands and networksandbox-limits

Isolation answers where the work happens. Limits answer what it can reach from there. Which paths may be written, which commands may run, whether anything may leave the machine. Stated per task rather than globally, because the task that regenerates a lockfile legitimately needs the network and the task that edits a component does not.

Two rules keep this from becoming theatre. The limits are declared where a person can read them, not buried in the agent's instructions where they are a suggestion. And exceeding them ends the run rather than printing a warning nobody sees.

Layer five

Verification: what must be proven before you look

Verificationverification

Agents are good at producing code that reads correctly. Review is where that becomes expensive, because plausible wrong code costs more attention than obviously wrong code. Verification is everything that happens before a person spends any attention at all, and its job is to make sure what arrives has already survived every check a machine can run.

The gate script owns the verdictgate-verdict

Checks run in one script that ends with a single line stating the result. Nothing is allowed to paraphrase it. An agent reporting that everything passed is a claim; the line is evidence, and the two are not interchangeable.

The behaviour that earns its keep is what happens when a required check is missing. A repository with no test command must not produce a green run. It produces a misconfigured verdict and stops, because silence and success are indistinguishable otherwise and only one of them is safe.

Holdout testsholdout-test

A test the implementing agent never sees cannot be optimised against. When the agent writes the tests and then makes them pass, a green suite means the code agrees with itself. Keeping some behavioural checks out of reach turns passing back into evidence about behaviour.

They are not a replacement for tests written alongside the change. They are the independent sample, and a handful covering the contract is worth more than a large suite the agent could read.

The writer never grades the workcold-verifier

Verification is delegated to a second agent that receives the diff and the task, and explicitly not the account of how the work went. Told what was attempted, a reviewer anchors on it and starts confirming rather than checking.

What this catches in practice is not syntax. It is the change that passes its tests while doing something the task never asked for: widening what gets stored, altering an unrelated behaviour, weakening an assertion to make a failure go away.

Revert the fix and watch the test failnegative-proof

The strongest check available, and no gate can make it. Take the new test, undo the change it was written for, and confirm it goes red. If it stays green the test proves nothing, and the run says so rather than shipping a passing suite that was never connected to the behaviour.

This one line of reasoning is the most useful thing in the whole system for most teams, and it applies with no agents involved at all.

Code decides what a verdict may claimevidence-rule

After the agent has finished talking, ordinary code reads the artifacts the run produced and decides what the result is allowed to say. A pass whose test output cannot be found is downgraded. A recommendation with no citation of the thing it rests on is downgraded. The agent's description of the run is never consulted for any of this.

Let the agent investigate freely, then let deterministic code decide what it is permitted to assert. Freedom where judgement helps, and no freedom at all in the sentence a person will act on.

One definition, checked from every sidecontract-drift

When a type is restated in three languages, the three restatements disagree eventually, and the disagreement is found in production. Keeping one definition and asserting each implementation against it turns that into a test failure at the moment of the change.

For a factory it does something more specific. It gives the cross-stack task a real shape: edit the shared definition and three suites go red at once, in three languages, which no single-language demonstration can show.

Layer five, continued

Self-healing: failing usefully, and stopping

Doer and Testerdoer-tester

Two roles rather than one. The Doer implements. The Tester decides whether the result meets the task, and when it does not, hands back the reason attached to the failure rather than a bare rejection. The next attempt starts from that reason.

Splitting the roles is what makes the second attempt cheap. One agent grading itself has already spent its reasoning on the version it produced, and tends to defend it.

A loop that cannot end is not a loopexit-criteria

Every cycle needs three declared endings: it passed, it ran out of attempts, or it exceeded its time. Without the second and third, a task that cannot be done consumes attempts until somebody notices, and what somebody notices first is the bill.

Escalation is a real outcome, not a failure of the design. The item goes back to a person with the attempts recorded and the reason the loop gave up, which is more useful than a run that is still going.

Measure where the time actually wentlatency-budget

The surprise on a first real run is that generation is rarely the slow part. Time accumulates in setup, in repeated checks, in verification that replays work already done, and in the stretch where the run is waiting on a person and nothing says so.

So each stage is timed separately and recorded: claiming the item, assembling context, implementing, gates, verification, and human wait. Every figure quoted in these pages is read from that record by a test, which is why none of them can drift from the runs that produced them.

The button that opens a session is not always called the same thing. A resting card offers Investigate, a card the factory is working offers Build, and Open session appears once a session exists and is idle. Follow the card, not the label: whichever button is on it is the one that opens what the run is doing. A run sheet that named a fixed button sent a presenter hunting for one that was not there.

Without per-stage numbers the only available response to a slow factory is to make the model faster, which is the one thing you do not control.

Layer six

Delivery: how finished work reaches a person

Deliverydelivery

The last layer is the one most demonstrations skip, and it is where trust is actually built or lost. Work has to arrive somewhere a person already looks, carrying enough evidence to be judged, and the decision to ship has to stay with someone accountable for it.

The queue is somewhere you already lookwork-queue

State lives in the issue tracker: labels for the stage, a structured comment for the handoff between stages, a branch for the claim. No database, no dashboard to keep alive, and nothing lost when a session ends.

The reason is durability rather than convenience. A run that dies halfway leaves its state in a place the next run and a curious human can both read, and neither of them needs the conversation that produced it.

A pull request that arrives with its evidencedraft-pr

The unit of delivery is a draft pull request carrying what happened: the gate verdict, the independent verdict, the negative proof, the stage timings and what it cost. A reviewer opens one thing and can see whether the work was checked before deciding whether it is right.

Draft is deliberate. It signals that a machine produced this and a person has not yet stood behind it, which is exactly the state it is in.

Nothing merges itselfhuman-merge-gate

No tier, no confidence score and no run of green results changes this. The pipeline stops at a reviewed pull request and a person decides. The hooks in the repository catch the obvious routes, and the enforcement that counts is a branch protection rule, because a guardrail an agent can edit is not a boundary.

This is also the answer to the question every room asks. The factory does not remove the reviewer. It makes sure that by the time the reviewer arrives, the machine has already done everything a machine can do.

The run recordrun-record

One immutable file per run: what was attempted, which files changed, every verdict, the timings, the cost. Appended to, never rewritten, because the value is in comparing the tenth run to the first.

It is what turns an opinion about whether this is working into a measurement, and it is what the console in this repository displays.

The same factory, four companies

Who does what, under each shape

The four profiles in profiles/ are usually read as a table of permissions. That is the least interesting thing about them. What each one really describes is a division of labour: who files the work, who decides it is worth doing, who accepts the approach, who reads the diff, who presses merge, and who gets woken up when it was wrong.

Read the four together and the argument becomes hard to avoid. None of them is more advanced than the others. Each moves the same set of decisions to different people, and each pays for that somewhere.

Solo

One person files, decides, accepts, reads and merges. The factory starts its own runs and approves its own plans, because the only reviewer is the person who will read the diff before merging anyway, and a gate between an author and themselves is ceremony.

The queue cap is one. That number surprises people until they think about it: a solo developer with three things waiting is not three times as productive, they are a bottleneck with a backlog. The constraint worth declaring here is attention, not capacity.

The money path is build, which reads as reckless and is not. The gate has moved to merge, where this person reads every line regardless. Moving it earlier would add a step that the same human performs twice.

Startup

A few people file and one of them accepts. Runs still start on arrival, because waiting for a person to press start on an obviously good issue is a tax nobody is paying for. Plans no longer approve themselves.

That single change is the whole shape. A small team shares the cost of being wrong without sharing the context that would have prevented it, so somebody reads the approach before code exists. The money path is propose for the same reason.

The queue cap is three. Above that, the person accepting plans becomes the constraint and the factory is generating work faster than the team can agree to it.

Scaleup

Teams own areas. Somebody files, the owning team triages, and a person on that team starts the run deliberately rather than letting arrival trigger it. The money path is refuse, because it has an owning team and an item that reaches it belongs in their queue rather than in a plan written by whoever filed it.

This is the first shape where the answer to "who decides this" is a different person from "who noticed it", and most of the friction in a scaling engineering organisation lives in that gap. The ownership graph is where that gets written down instead of argued about on the day.

The queue cap rises to five, because there are more people who can read a plan. It does not rise further, because the reviewers are still individuals with calendars.

Enterprise

Nothing is planned or implemented until a person has accepted the item. The tier is controlled rather than supervised, and the difference is real: work does not begin on arrival at all.

The money path is refused and protected, so a run stops at the boundary rather than producing a plan nobody may act on. The contract package is refused too. What an agent may do here is investigate, and propose.

The queue cap falls back to two, which reads as a mistake and is not. The constraint is no longer how many plans a team can read; it is how many items a change process can carry at once. A larger cap would queue work against a slower gate and call it throughput.

A team that cannot say which of these four it is will configure its factory by accident, and the accident will be whichever shape the tool shipped with.

Measured, not asserted

A rule written in a prompt is a request, and a rule written in a gate is a limit

Everything above this describes how a factory is supposed to behave. This section describes how one actually behaved, on the runs that produced the figures and the screenshots in this material, and the two are not the same. The gap is not a defect report. It is the most useful thing in the workshop, because it is the difference between the two systems in this repository, and that difference is the whole argument for building the layers by hand before buying them.

The hand-built pipeline calls decide() before anything runs. Mastra Factory tells the agent about the same ownership graph in AGENTS.md and then dispatches the work. One of those systems consults the rule and the other repeats it. Nothing in the second one is broken or misconfigured: the agent was told, in the file the product reads, and the engine simply has no code that asks the graph a question before writing a file.

A limit that depends on the agent choosing to honour it is a limit you have already lost. The test is not whether the model complied on your run. It is whether any code would have stopped it if it had not.

The same change, put to both systemstwo-answers

The cleanest evidence in the material comes from the route designed to be boring. An issue asks for a Contributing section in the README. The agent triaged it, planned it, built it and opened a pull request, and the run sheet shows that pull request being approved. Then 01-clean-path.spec.ts hands the very same list of changed files to decide(), reading the very same .factory/targets.json, and gets the opposite answer: REFUSE, because README.md has no owner in the graph and falls through to the repo target, which is set to refuse.

Two systems, one repository, one diff, two answers. The model is not the variable. The variable is that one of them calls a function.

Run the same route twice and the agent does not always make the same choice. It advanced its own plan on one run and waited on the next. It opened a pull request on one run and pushed a bare branch on another. This is the part worth sitting with, because it defeats the obvious objection. If the behaviour were reliably wrong you would notice in a week and fix the prompt. It is reliably unreliable, which means your demonstration passes, your pilot passes, and the run that matters is the one nobody watched.

That test fails if the page cites a finding no run produced, and it also fails if a run recorded an instruction the model ignored and this page does not mention it, which is the failure mode of anybody writing up their own demonstration.

The last column says how strongly each row is evidenced, because they are not all evidenced the same way and a table that hides that is doing the thing this section exists to warn about.

  • The record means the counter in evidence/prompt-vs-gate.json has watched the claim fail on a run it counted, and the gate will fail this page if the row is removed while that stays true.   • PR 544 and PR 547 are pull requests still open to inspection in the example repository. The first changed README.md, a path the graph refuses. The second changed packages/contracts/**, a propose path, in the same commit range that wrote its own plan to .artifacts/plans/ and then carried on without anyone reading it. Go and look at them.

That distinction is the honest shape of the evidence, and it is worth saying to a room out loud. The strongest rows are the two you can click on. The weakest are the ones you have only my word for, and the reason the counter exists at all is that my word is not the standard this repository holds everything else to.

What each of these costs, and what to do insteadwhat-to-do

Read the table as four distinct problems rather than one, because they need four different answers and only the first is about autonomy levels.

An advisory level costs you the reason you wrote it down. If propose cannot hold work at the boundary, then the ownership graph is documentation and the only real control left is the branch protection rule at the end. The fix is not a firmer sentence in AGENTS.md. It is a check that runs against the diff before the pull request can merge, reading the same graph, and refusing paths the graph refuses. That check is the one thing in this material you should port into your own repository first, because it works whatever agent you buy.

A silent refusal costs you the ability to tell deciding from dying. An issue with no branch, no comment and no activity looks the same whether the factory declined it on purpose or fell over. The charter says to record the reason and route the item to a person, and no code makes that happen. Anything that stops should have to say so in a place a person already looks.

A model that cannot tell it is guessing will guess. "Ask when unsure" is the weakest instruction in any prompt, because the failure requires the agent to notice its own uncertainty, and the runs where it did not notice look exactly like the runs where there was nothing to ask. Replace it with a rule that does not depend on noticing: an issue that names no owning service does not reach the build stage.

Two representations of one verdict will disagree. The comment is what the reviewer writes and what a person reads. The label is a projection of it that nothing reconciles, so a pull request that had just been approved read as unlabelled, and anybody filtering a queue by label would not have seen it. Pick which one is the record and derive the other from it.

These four are worth more to the room than a run where everything went right. A clean demonstration teaches that the architecture is plausible. This teaches where it actually gives way, which is the only part anybody will have to deal with on a Tuesday.

What survives the products

The patterns that outlast both products

Both of the systems in this repository will be replaced. These will not. Each one is written the same way: the problem it answers, the forces pulling against each other, the move, what it costs, and where it shows up in the thing built by hand and in the thing bought off the shelf.

A pattern with no cost listed is a recommendation, and a recommendation is the kind of advice you cannot argue with.

A prompt is not a gateprompt-is-not-a-gate

Problem
The rules an agent must follow have to be written down somewhere, and the obvious place is the prompt the agent reads.
Forces
A prompt is the cheapest place to put a rule, it needs no code, and it reads convincingly to whoever wrote it. A gate costs work and has to be maintained. Meanwhile the agent complies often enough that the difference stays invisible until the run that matters.
The move
Write every rule twice. Once in the prompt, so the agent knows what is wanted, and once as code that runs before or after the work and can refuse it. If the second copy does not exist, say out loud that the rule is advice.
It costs
Two places to change when a rule changes, and a test that holds them together.
Here
steps/01-boundary/policy.ts reads the ownership graph and refuses before any agent starts, which is why make prove can break it on purpose and watch it fail.
On a platform
The same graph is described to the agent in AGENTS.md and consulted by nothing. The run recorded in the findings built a refused path and skipped an acceptance step, both while being told not to.

The executor is an interfaceexecutor-as-interface

Problem
Every part of the system needs an agent to do work, and binding to one makes the whole thing a wrapper around a product that will change.
Forces
Testing wants determinism and no spend. Teaching wants a real agent. Buying wants the freedom to change the agent later. All three pull against hard-coding one.
The move
Define an executor as any command that takes a prompt on standard input and exits. Everything above it depends on the interface, never on the product.
It costs
One indirection, and usage figures an agent reports rather than ones you measured.
Here
steps/lib/executor.ts, with a replay executor that makes make check free and offline.
On a platform
The agent role on a working phase. Swapping the model is a settings change rather than a code change.

The name is the claimdeterministic-claim

Problem
Two scheduled runs wake up for the same item and both start work on it.
Forces
A lock table is correct and is a service to operate, with an availability story and a question about what happens when a holder dies.
The move
Derive the branch name from the item so both runs compute the same one, and push without force. The first push creates the ref and the second is rejected.
It costs
Nothing, unless somebody adds a force flag, which is why there is no flag to pass.
Here
branchFor() in steps/02-execution/worktree.ts, proven by a real push race in the tests.
On a platform
The server owns session identity, so the race does not arise. The idea still applies to anything you schedule yourself.

A missing check is louder than a failing onefail-closed-gate

Problem
A repository with no test command produces a run that looks exactly like a passing one.
Forces
Absence and success are indistinguishable from outside. Treating absence as success is the default in almost every pipeline, because it takes no code.
The move
Make the gate report three states rather than two. Missing is neither a pass nor a failure, and it stops the run.
It costs
A repository that has not finished wiring its checks cannot ship through the factory yet, which is the point.
Here
steps/04-verification/gate.ts returns MISCONFIGURED with exit 2.
On a platform
A tool result rule reading the verdict, which refuses to read a missing check as either outcome.

One line nothing may restateverdict-line

Problem
An agent reports that the checks passed, and that report is the only thing anyone reads.
Forces
An agent summarising is useful everywhere except in the sentence somebody will act on.
The move

Tests the writer never sawholdout-sample

Problem
The same run writes the code and the tests, so a green suite means the code agrees with itself.
Forces
Tests written with the change are the most useful ones to have. They are also the least independent.
The move
Keep a small set of behavioural checks out of reach of the implementing agent and run them afterwards.
It costs
A second place to maintain, and it must stay small or it becomes a second suite.
Here
steps/04-verification/holdout/, outside the target and never routed.
On a platform
A checking phase whose role has different tools from the building one.

Forces

The move
Give a second agent the task and the diff, and deliberately not the story of the attempt.

Minutes per change, and occasional rejections of work that was fine.

Problem
A test that has never been red is not known to test anything.
Forces
Nobody wants to break working code to check a test. It is also the only check that proves the test is connected to the behaviour.

The limit is review attentionback-pressure

Problem
Generation is cheap, so the queue of things waiting for a person grows without bound.
Forces
More agents feels like more throughput. The binding constraint is one person understanding a change well enough to stand behind it.
The move
Cap how many items may wait on a person, and refuse to start work when the cap is reached.
It costs
Idle capacity, which is the correct thing to have.
Here
STOP_IF: awaiting_review >= n in the charter, checked before anything else runs.
On a platform
Not built in. It is yours to add, and it is the first thing people delete.

Freedom follows blast radius, not sizeautonomy-by-consequence

Problem
Deciding what an agent may do unattended by how big the change is.
Forces
Size is easy to measure and is the wrong axis. A ten thousand line migration on an unlaunched project is safer than fifty lines in a payment path.
The move
Grade autonomy by how bad the worst outcome is and how easily it is undone, per area rather than per repository.
It costs
Somebody has to decide, area by area, and write it down.

The autonomy column in .factory/targets.json, with a reason beside each.
On a platform
A transition policy, which can also demand recorded acceptance before code exists.

Some paths are never touchedprotected-path

Problem
The area where a mistake is most expensive is the area an agent will eventually touch.
Forces
A blanket refusal stops the factory being useful. No refusal at all means the first surprise is the expensive one.
The move
List the paths that are never modified unattended, each with the reason, and have the list protect itself.

A route for work that legitimately needs those paths, which is a person.

The protected block in the charter, which protects the charter and the graph beside it.
On a platform
The same list, expressed in the policy that allows or rejects a move.

Problem

Forces
Each addition works, which is why it keeps happening. The sentence that matters is now competing with forty that do not apply.

Hand back the reason, not the rejectiondoer-and-tester

Problem
A failed check comes back as a status, so the next attempt repeats the mistake.
Forces
One agent grading its own output has already spent its reasoning defending it.
The move
Split the roles. The tester returns what failed, where, and what should have been true, and the next attempt starts from that.
It costs
Two roles to run, and a loop that needs declared endings or it will not have one.
Here
handback() in steps/05-loop/loop.ts, with attempt and time budgets.
On a platform
A retry outcome on the checking phase, routing back to building.

Separate where work is from who decidesphase-and-policy

Problem
Process and permission get tangled, so changing one changes the other by accident.
Forces
A board is about where work is. A policy is about who may move it. Mixing them makes every rule a layout change.
The move
Declare phases and the moves between them, then declare separately which moves a person must make.
It costs
Two things to read instead of one, and worth it the first time the process changes.
Here
The graph declares areas and the charter declares who decides, and neither restates the other.

defineBoard() for phases, transitionPolicy for who may move a card.

The same architecture, bought instead of built

On a platform

Phases are the layers, named differentlyboard-phases

A hosted factory gives you a board whose columns are stages, where entering a stage starts an agent in a declared role and leaving one runs an action. Intake, triage, planning, building, review, done. The mapping to what this repository builds by hand is close to one to one, which is the point of building it by hand first.

Recognising the mapping is what makes the buy decision an engineering decision. You are not choosing between a product and nothing. You are choosing who maintains the parts you now understand.

The policy is still yourstransition-policy

The part that never transfers is the judgement. A platform supplies the board, the sandboxes and the sessions; what may move to done without a person, which work needs recorded acceptance before any code exists, and where the money path sits are still yours to state. On a platform they are a function that allows or rejects a move.

So the last step here is not a migration. It is the same charter expressed against a different substrate, which is the honest test of whether the architecture was real.
